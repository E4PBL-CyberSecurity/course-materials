# 公開ネットワーク教材の作成方針と確認

学生用原稿は`handbook/`の全体案内と第1〜11章です。実験教材は別の非公開リポジトリで管理します。 掲載対象と付属ファイルは`publishing/documents.mjs`を正本とします。

USBメモリの呼称は「インストーラーUSB」（ISOを書き込む媒体）と「インストール先USB」（VyOSを書き込み、完成後は起動・設定保存に使う媒体）に統一します。インストール前後で名称を変えません。

Linuxディストリビューションの名称は「Kali Linux」「Ubuntu」と表記します。本文・見出し・図表のキャプションで名称を省略しません。コマンドの登録名、ファイル名、URLは実際の識別名を保ちます。

WSL内の授業用アカウントは、Kali Linuxのユーザー名・パスワードをともに`kali`、Ubuntuのユーザー名・パスワードをともに`ubuntu`とします。Ubuntuの初回ユーザー作成でWindowsのユーザー名が候補に出ても、`ubuntu`を入力する手順にします。ユーザー名を含む操作やパスを、全員が手順書の記述どおり使えるようにするためです。

## 教材作成方針：説明と指示の必要性を判断する

説明文は、次の優先順位で掲載する内容を選びます。

1. **その場の作業に必要なこと。** 操作する機器・画面、操作方法、入力する値、コマンドの目的、結果の読み方と完了条件を示します。
2. **他の手順との関係や、承知しておく必要があること。** 前提となる設定、後の作業への影響、データ消去や認証情報の扱いなど、作業の判断に必要なことを示します。
3. **学生がまだ知らない基礎知識。** サイバーセキュリティ、ネットワーク構成、Linuxで前提となる用語や仕組みを、手順との関係が分かる形で説明します。

この三つに当てはまらない説明や指示は書きません。作成者の検証事情、使わない操作への注意、同じ内容の言い直しを、学生用手順へ持ち込みません。検証状況は検証記録、教員の準備事項は教員用の箇所に記載します。

執筆・改訂後は、学生がその文章を読んで作業する場面を想定して読み直します。「何をするか」「何を入力するか」「何が表示されればよいか」が分かることを確かめ、各文と指示を上の三つの基準に照らして、該当しないものを削ります。操作・判断に必要な説明や、まだ知らない基礎知識は残します。

この方針は2026年10月24日の授業担当者の指示に基づき、今後の教材作成・改訂にも適用します。

コマンドのオプションは、作業に必要なものだけを使います。既定値と同じ内容を指定するオプションは付けません。Windowsでの鍵作成は`ssh-keygen.exe`を直接起動し、保存先やパスフレーズは対話形式で入力します。

SSH公開鍵認証の手順は、鍵の作成・送付・機器の標準機能による取り込み・通常の`ssh`での接続確認を基本とします。公開鍵を使うだけの手順に、鍵の手作業での分割、ssh-agentの設定、認証方式を制限する接続オプション、パスワード認証の無効化を加えません。

授業用Windows PCでは、学生本人のユーザーアカウントに管理者権限があります。学生用の導入手順では、必要な箇所に「ターミナル（管理者）」の起動や「ユーザー アカウント制御」の承認手順を記載します。WSLの導入・登録は学生本人のWindowsアカウントで行います。

## 教材作成方針：標準の画面操作を学ぶ

Windowsの設定画面へは、「スタート」や「設定」の分類をたどって進みます。学生が手順を忘れても、画面の項目名や分類を手がかりに目的の設定へたどり着ける力を育てます。操作を短くするためだけに、設定画面の実行名や特殊なショートカットを暗記させません。ネットワーク設定は「ネットワークとインターネット」、Windowsの版確認は「システム」から開く手順にします。

Windowsでのフォルダー作成やファイルのコピーは、エクスプローラーで行う手順にします。学生がPowerShellの変数や処理結果を理解しているとは想定せず、コピー先に表示されるファイル名など、画面で判断できる完了条件を示します。

画面の入口、選択する項目、入力する値、保存後の確認まで示します。CLI自体を学ぶ必要がある作業では、コマンドの目的と結果の読み方を説明します。最初にターミナルを使う箇所には、アプリの起動からPowerShellの入力待ちの確認まで記載します。この方針は2026年10月24日の授業担当者の指示に基づきます。

## 教材作成方針：ThinkPadでのキー入力を減らす

学生はキーボード操作に不慣れで、ThinkPadも使い慣れた機器ではありません。キー入力がときどき意図どおりに動作しない環境でもあるため、入力そのものと、誤入力後のやり直しを大きな負担として扱います。ThinkPadの本体画面・キーボードで行う手順は、コピー＆ペーストを使えず、すべて手入力する前提で作成します。

使用機種は日本語キーボードのThinkPad E530cです。VyOSの初期配列はUSのため、ログイン直後、記号やパスワードを入力する前に日本語配列`jp106`へ切り替えます。インストール先にも設定を引き継ぎ、再起動後の保持まで手順に含めます。

- **必要な操作だけを掲載する。** 学習目標、作業の進行、誤操作の防止に必要なコマンドと確認に絞ります。作成者の検証や情報収集のためだけの操作、同じ確認の不要な繰り返しは学生の必須手順に入れません。
- **書式指定を省く。** 表示列や見た目を整えるだけのオプションは付けず、標準表示で目的を達成できる最短のコマンドを使います。例として、ディスク一覧は`lsblk`だけを入力します。標準表示にない情報を前提にした説明も残しません。
- **入力しにくい要素を増やさない。** 長いパス、パイプ、引用符、記号を多用する式などをThinkPadで手入力させる必要があるか見直します。短縮のために別の設定やエイリアスを入力させ、総操作数を増やすことも避けます。動作に必要な引数・オプションは省略しません。
- **操作順序と画面の見方で補う。** 追加の表示指定で情報を増やす前に、手順を工夫できないか確認します。例として、インストール先USBは接続前後の`lsblk`を比べ、新しく増えたディスクを識別します。起動に使っているインストーラーUSBは外しません。
- **操作場所を明示する。** ThinkPadで必要な初期設定を終えたら、可能な作業はWindows PCからのSSH接続で行います。Windows PCでコピー＆ペーストできる手順と、ThinkPadで手入力する手順を区別します。長いコマンドの入力や詳細な記録は、可能ならWindows PC側へ移します。
- **命令と結果の意味を説明する。** コマンド名から意味を推測できることを前提にしません。特に`set`は変更の準備、`commit`は動作への反映、`save`は次回起動用の保存と区別します。確認コマンドを載せるときは、実行前にその確認目的を説明します。出力例と、どの欄を見て何を成功と判断するかも示します。複数のコマンドをまとめて載せる場合も、各コマンドの目的と結果を個別に説明します。配線前後など、その段階で正常な表示が変わる場合も明記します。
- **必要な確認は残す。** 入力を減らすために、消去対象・インストール先の識別、パスワードの設定、設定保存、完了確認を省きません。改訂時は、手入力する文字数・記号・操作回数・誤入力時のやり直しまで含めて必要性を点検し、短くしたコマンドと説明が対象のVyOSで成立することを確認します。

この方針は2026年10月24日の授業担当者の指示に基づき、今後の教材作成・改訂にも適用します。

## PDFとWebを生成して確認する

既存のAstro Starlightとminitypeを使い、同じMarkdownからWeb・PDFを生成する構成を引き継ぎます。Node.js 22で依存を準備し、`publishing`で`node build.mjs --publish`を実行します。ここでの`--publish`は検査後のローカル`docs/`更新だけで、GitHubへのpushや公開設定変更は行いません。`docs/`は直接編集しません。

本リポジトリの設定に含まれる原稿・付属ファイルだけを生成し、冊子と前後移動は`publication.chapterCount`で指定した先頭の文書を使います。分離前の全手順冊子を再利用しません。生成後は既存の`node check.mjs`とWeb・PDFの表示確認を行います。

公開はGitHub側の履歴と公開設定を確認してから別工程で行います。現在の新しいローカル履歴へ、非公開側の履歴をマージ・コピーしません。
